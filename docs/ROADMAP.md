# PlanStride delivery roadmap (revision 2)

This revises `assessment/ai_weekly_planning_saas_full_roadmap.pdf` (revision 1)
against the brief (`assessment/se-intern-weekly-planner-assement.pdf`, SE-INT-04)
and against what the Launchbase template actually does. Revision 1 is a sound
outline: the priorities, phases and acceptance checklist are kept. This revision
fixes what it got wrong or left open, records the decisions it deferred, and
tracks status.

## 1. What changed from revision 1, and why

**Gaps in the template that revision 1 didn't catch**

| # | Finding | Why it matters | Resolution |
| --- | --- | --- | --- |
| 1 | Launchbase never checks `is_active`, at login or on token use. Its own test asserts that a deactivated user still gets `200`. | "Deactivate an account" would do nothing. | The check runs on every authenticated request, on both surfaces. Login answers `403 account_deactivated` only after the password checks out. The template test is reversed. |
| 2 | The template's `AGENTS.md` says tests are optional. | The brief says tests are required and that the brief wins. | `api/AGENTS.md` now requires tests for every API change. |
| 3 | The internal console can create users with the admin flag, and can hard-delete users. | Staff must come only from `manage.py create-user --admin`, and a hard delete orphans organizations and history. | Staff grants removed from the console API; delete replaced by deactivate and reactivate. |
| 4 | The template's login does no Argon2 work for unknown emails. | Response time reveals which emails have accounts. | Equal work on every path, on both surfaces. |
| 5 | The template's routers are mounted sub-apps. | Test dependency overrides on the root app don't reach them. | `conftest.py` overrides each sub-app. |

**Decisions revision 1 deferred, now made**

| Topic | Revision 1 | Decision (details in `docs/ARCHITECTURE.md`) |
| --- | --- | --- |
| Who approves when someone is on several teams | Not addressed | The lead of any team both are on. A lead's own plan goes to the lead of another team they're on. Self-review is impossible, and a stale lead loses rights immediately. |
| Who can read a plan | Not addressed | Drafts: the author only. Submitted: teammates, leads, org owners and admins. Everyone else gets 404. |
| 404 or 403 across organizations | "Must be blocked" | 404 for anything outside your organizations (existence isn't revealed); 403 with a reason inside your own. |
| `is_admin` versus the org admin role | "Use clear names" | The ORM attribute is `is_platform_staff` (the column name is kept for the documented CLI). "Admin" in code means only the customer role. |
| Returned plans | Back to draft, or a documented "returned" state | Back to draft with `review_decision = "returned"` and the comment kept on the plan. |
| `last_active_at` | A stored column | Derived in SQL from plans, tasks, AI calls and joins. Nothing to keep in sync. |
| Invitations | "Token or token hash" | SHA-256 hash only, single-use, 7-day expiry, revocable, row-locked on accept. Shown once. |
| Monday keys and one plan per week | Validate in the API | Also enforced by Postgres: a CHECK on ISO weekday, a unique (org, user, week), and a partial unique index for one main task per plan. |
| Cross-organization team seats | "Prevent" | A composite foreign key makes them impossible at the database level. |
| AI cost visibility | Count calls | Calls plus tokens and latency per organization, feature, day and error type. |
| AI quota protection | "Avoid per-keystroke calls" | Calls only on an explicit click, plus a per-user throttle (6/min) counted from the usage log. |
| Failure logging | "Log each call" | Usage rows are committed before the error response, so failures are counted too. |
| Staff access to plan text | "Make a deliberate call" | No. Counts only, and a test enforces it across every internal endpoint. |
| Optional feature | "Pick at most one" | **Look back before planning**: a tenancy-safe agent tool feeding `carry_over` findings. It strengthens the core review rather than adding a separate surface. |

**Timebox.** Revision 1 fits the brief's ~12 hours; the build took 18. The work
came out larger, mainly from the tenancy test matrix, the failure handling, the
visual polish and tuning the AI on the live model (section 4). The brief values
a solid core over extras, so the extra time went there.

## 4. The live run, and what's open

**Done: the live run against Gemini.** With a key in `api/.env`, both agents
ran against `gemini-3.5-flash-lite` (available to the key; about 2 to 5 seconds
a review) through the API and in the browser, on the seeded plans. The first
run worked end to end, typed output included, and showed four problems, now
fixed:

| Seen live | Fix |
| --- | --- |
| Findings said "T1 is an activity": the prompt's short keys leaked into the text | Instructed never to; `unkey` rewrites any that slip through |
| No `carry_over` finding in three runs, although the tool returned last week's unfinished checkout work | The tool also returns the member's note; the instructions say how to compare; carry-over takes priority over "not checkable" for the same task |
| Made-up figures in rewrites ("under 500ms", "by 15%") | Instructions forbid any number the plan doesn't contain and say how to phrase a check without one |
| Once carry-overs worked, some were invented (Tom's Postgres work "carried over" from unrelated retry work) and strong plans got nitpicked | Carry-overs are checked against the look-back (output validator, then normalization); examples of tasks that already pass; "ready with no findings" made explicit |

It also showed the drafter writing activities ("Configure Okta") that the
reviewer then flagged, and putting a second project into the sub-goals; its
instructions now match the reviewer's standard. Seeding fix: Tom's last-week
note described different work from the plan it closed.

**Open:** only committing and archiving (section 5). What the product doesn't
do yet, or hasn't been verified to do, is listed under "What isn't done" in
`SUBMISSION.md`.

## 5. Packaging (yours to run)

Nothing has been committed. The brief asks for small commits as you go; one way
to split the work:

1. `chore: start from Launchbase` (the template as cloned)
2. `feat(brand): PlanStride name, logo and favicon`
3. `feat(api): organizations, teams, plans and migration`
4. `feat(api): AI review and drafting with Pydantic AI`
5. `feat(api): internal endpoints, seed command and tests`
6. `feat(app): sign-up, my week, approvals, teams and members`
7. `feat(internal): staff console`
8. `feat(site): landing page`
9. `docs: architecture, roadmap and submission notes`

Then:

```bash
git add -A
git commit -m "Final submission"
git archive --format=zip -o assessment.zip HEAD
```

Unzip `assessment.zip` into a fresh folder and follow the README from scratch
before uploading. `api/.env` is gitignored, so your key never goes into the zip.
